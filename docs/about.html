About & Methods

How this benchmark was designed, what it measures, and how scores are computed.

Project Overview

The UCSB AI Services Evaluation Suite is a systematic benchmark designed to assess the capabilities of large language models (LLMs) available through UCSB-managed AI infrastructure. The goal is to give researchers, students, and staff an objective basis for choosing which service and model best fits their workload — weighing accuracy, throughput, and availability.

The benchmark covers six task categories drawn from real research computing workflows at UCSB: code generation, metadata generation, literature synthesis, data interpretation, OCR/document extraction, and vision question answering.

Infrastructure

Service Infrastructure Endpoint Notes
GRIT 🖥️ On-premise · Ollama llm.grit.ucsb.edu UCSB General Research IT HPC cluster. Largest model catalog.
CIT 🖥️ On-premise · Ollama api.ai.college.ucsb.edu College of IT servers. Higher throughput than GRIT for same models.
AICommons ☁️ Cloud · Amazon Bedrock zkh52rh785.execute-api.us-east-1.amazonaws.com AWS-hosted. Diverse catalog: Claude, GPT-4o, Amazon Nova, Llama 4.
Why infrastructure type matters: GRIT and CIT serve all models locally — model weights run on UCSB hardware, so throughput is determined by GPU capacity and network load on university servers. AICommons routes requests through Amazon Web Services (Bedrock), which provides scalable but metered capacity. The same model binary will produce identical outputs on both infrastructure types, but throughput (tokens/sec) and latency will differ.

Benchmark Datasets

Three benchmark datasets were used, covering increasing complexity and modality:

Dataset v1 — Standard (12 tasks)

Twelve text-only tasks across four categories. Designed to represent common research data workflows: analysing tabular data programmatically, writing structured metadata, synthesising scientific abstracts, and interpreting statistical outputs. All tasks use a 1–5 scoring scale.
Category Tasks Description
Code Generation 3 Write Python/pandas to filter, aggregate, and summarise a CSV dataset
Metadata Generation 3 Generate DataCite-compliant JSON metadata records from dataset descriptions
Literature Synthesis 3 Extract structured information from scientific abstracts (methodology, findings, limitations)
Data Interpretation 3 Multiple-choice: interpret correlation matrices, regression outputs, and SST distributions

Dataset v2 — Harder (12 tasks)

Same four categories with scientifically more demanding prompts: tasks require numerical precision (e.g. computing Pearson correlation to 4 decimal places), anti-hallucination reasoning, detection of internal contradictions in abstracts, and advanced statistical interpretation (Simpson's paradox, AIC model selection, autocorrelation).

Multimodal Dataset (6 tasks)

Vision-language tasks using two historical document images: a 19th-century Spanish newspaper scan and a historical catalogue card.
Category Tasks Description
OCR 2 Extract structured weather table and bibliographic header from newspaper scan
Document Extraction 1 Extract all fields from a historical catalogue card
Vision QA 3 Answer specific factual questions about image content (exact match + judge-scored)

Scoring Methodology

All tasks use a 1–5 integer scale. The scoring method depends on the task category:

Category Scorer Type Score 5 Score 1
Code Generation programmatic Code executes and produces the correct numeric output Code fails to run (syntax error / exception)
Metadata Generation programmatic Valid JSON, all required schema keys present, values correct Output is not valid JSON
Data Interpretation exact match Correct MCQ letter selected (A/B/C/D) Wrong answer
Literature Synthesis LLM judge All required fields extracted accurately, no hallucinations, valid JSON Missing fields, fabricated content, or completely wrong
OCR programmatic + LLM judge All table fields correctly extracted (field-accuracy ≥ 90%) Cannot parse response or accuracy < 25%
Document Extraction LLM judge All document fields captured, no hallucinations Major omissions or fabrications
Vision QA exact match + LLM judge Correct answer (for exact-match tasks) or full credit from judge Wrong answer
OCR hybrid scoring: OCR tasks are first scored programmatically (field-accuracy comparison against ground-truth rows). If the programmatic score is below 4/5, the LLM judge is called as a second opinion, and the higher score wins. This gives models the benefit of the doubt for partial extraction.

LLM-as-a-Judge

For tasks requiring subjective evaluation (literature synthesis, OCR, document extraction, and some vision tasks), model outputs are evaluated by a second LLM acting as a judge. The judge receives the model output, the original prompt, and a detailed scoring rubric, then returns a structured JSON response with a score (1–5) and reasoning.

Judges Used

Judge Service Role
gemini-3.5-flash DreamLab Development judge — used during iterative benchmark development for cost efficiency
claude-v4.6-sonnet AICommons Production judge — used for all final benchmark runs; canonical scores on this dashboard
Judge conflict guard: The evaluation engine prevents a model from judging its own outputs. It detects conflicts by exact model name match, cross-service exact match, and 6-character family substring matching. If a conflict is detected, the alternative judge is used automatically.

Dashboard policy: Where both judges evaluated the same output, the dashboard defaults to Claude (production judge) scores. The Model Explorer page provides a toggle to view and compare both judge scores for literature synthesis tasks.

Token Budgets & Evaluation Scope

Each service has a monthly token budget enforced by the evaluation engine. Token consumption is tracked atomically across runs in .token_usage.json. Judge calls (which consume tokens from the judge's service budget) stop automatically when the monthly limit is approached — leaving a safety buffer.

Budgets: GRIT 10M · CIT 10M · AICommons 900K (strict 1M monthly cap with 100K buffer).

Reproducibility

The full evaluation suite is open-source. To reproduce any result:

uv run python run_eval.py --judge-service aicommons --judge-model claude-v4.6-sonnet

The --resume flag skips already-completed (service, model, test_id) triplets, making interrupted runs safe to continue. The --re-judge flag re-scores stored model outputs with a new judge without re-calling target models — useful for comparing judge quality without incurring additional inference costs.

Acknowledgements

🙏 DreamLab — Acknowledgement & Contribution

The UCSB DreamLab (litellm.dreamlab.ucsb.edu) made a significant contribution to this evaluation project. DreamLab provided access to a suite of Google Gemini models via a LiteLLM proxy, including: gemini-3.5-flash, gemini-3.6-flash, gemini-3.1-flash-lite, gemini-3.1-pro-preview, gemini-3.1-pro-preview-customtools, and gemini-3-flash-preview.

DreamLab's gemini-3.5-flash served as the default LLM judge throughout the iterative development of this benchmark suite, processing hundreds of judge evaluations and enabling rapid iteration. All final production results were re-judged with claude-v4.6-sonnet for comparability, but the DreamLab judge was integral to the benchmark's development pipeline.

DreamLab results are not included in the comparative dashboard because DreamLab cannot guarantee the continued availability of LLM inference services going forward. Including results from a service that may become unavailable would undermine the dashboard's usefulness as a guide for current service selection.

We thank the DreamLab team for their support of UCSB's AI research infrastructure and their contribution to this project.
